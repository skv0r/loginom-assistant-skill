# Workflow: обнаружение аномалий (LOF + sklearn kits)

Обобщённый паттерн для задач «норма vs аномалия» в Loginom 7.3 с **loginom_sklearn_meta** и **loginom_sklearn_kit**. Подходит для медицинских рядов, промышленных датчиков и любых tabular-данных с меткой класса.

## Постановка

- **Обучение:** только «нормальные» объекты (иначе LOF Novelty некорректен).
- **Валидация:** подбор гиперпараметров (k, contamination).
- **Тест:** финальная оценка качества (часто F1).
- **Скоринг:** все новые объекты прогоняются через обученную модель.

## Данные

| Элемент | Рекомендация |
|---------|----------------|
| Признаки | Числовые столбцы (z-score по train) |
| Метка | Бинарная после преобразования: 0 = норма, 1 = аномалия |
| Разбиение | `SAMPLE` ∈ {train, valid, test}; `IsTestSet` = (SAMPLE ≠ train) для kits |
| Seed | Фиксировать `RandSeed=42` в «Разбиение на множества» |
| ID | Уникальный столбец (OBJECT) для воспроизводимого merge |

Типичные доли: **70% / 15% / 15%** train/valid/test; train — только норма; valid+test — норма+аномалии со стратификацией.

## Сценарий A — подготовка (нативные узлы)

```text
Импорт(ы) → Объединение
  → OBJECT (калькулятор)
  → Фильтр CLASS=норма (только на ветке train-доли)
  → Разбиение 70/30 (последовательное, seed=42)
  → Объединение «остаток нормальных + все аномалии»
  → Разбиение 50/50 (стратифицированное по CLASS, seed=42)
  → Калькуляторы SAMPLE = train | valid | test
  → Объединение финального датасета
  → IsTestSet = (SAMPLE <> "train")
  → Публичный узел датасета (mvPublic) для сценария B
```

Проверки после выполнения:

- Общее число строк стабильно (не «прыгает» после разбиений).
- train без аномалий; valid и test содержат аномалии.
- Доли train/valid/test близки к заданным.

## Сценарий B — модель (kits)

```text
Ссылка на публичный датасет
  → Meta-scaling (обучение статистик на train)
  → preprocessing.Scaler (параметры; опционально отдельным узлом)
  → neighbors.LOF Novelty (novelty=true, k, contamination)
  → simple.fitter — fit на train-потоке
  → [опционально] Замена CLASS / Reform на train-ветке
  → model.fitter — сохранение модели
  → Фильтр SAMPLE=valid → model.fitter (порт скоринга / тестовая выборка)
  → Фильтр SAMPLE=test  → model.fitter (порт скоринга)
  → Изменение (служебные поля y_true / y_pred)
  → Замена: outlier_label (-1→1, 1→0) и CLASS (1→0, 2..K→1)
  → classification metrics (valid: Fbeta, test: F1)
```

### Критичные настройки

| Параметр | Значение | Зачем |
|----------|----------|-------|
| LOF `novelty` | true | обучение без «загрязнения» test-аномалиями |
| `n_neighbors` (k) | 15 / 20 / 25 | сетка по заданию |
| `contamination` (c) | 0.02 / 0.05 | сетка по заданию |
| metrics `average` | binary | двухклассовая задача |
| metrics `pos_label` | 1 | аномалия — положительный класс |
| metrics `beta` | 2 | если FN в 4 раза важнее FP (β=2) |

### Порт model.fitter

- **Обучение:** поток после meta-scaling **train** (норма).
- **Скоринг valid/test:** вход **meta-scaled ALL** (или эквивалент) + фильтр SAMPLE; подключать к порту **тестовой/скоринговой** выборки (`dd84ef4f-…` в типовых пакетах), **не** к порту обучения.

Типовая ошибка: valid/test подключены к train-порту или без meta-scaling — метрики «плавают» и не совпадают с offline sklearn.

## Преобразование меток для metrics

После LOF:

- `outlier_label`: **1 → 0** (норма), **-1 → 1** (аномалия).
- `CLASS` (если исходно 1=норма, 2..K=аномалия): **1 → 0**, **остальные → 1**.

Не дублировать противоречащие правила в нескольких узлах «Замена» на одной ветке.

## Подбор гиперпараметров

1. Для каждой пары (k, c) обучить на train, скорить **valid**.
2. Записать **Fbeta** (при β>1 акцент на recall / FN).
3. Выбрать max Fbeta; при равенстве — **меньшее k** (типичное правило методичек).
4. Финальный прогон на **test**, отчитать **F1** (и при необходимости полную матрицу).

Offline-проверка (Python/sklearn) по экспорту датасета — см. `scripts/validate_lof_metrics.py` (шаблон; пути задаёт пользователь).

## Интерпретация метрик

| Метрика | Смысл при аномалиях |
|---------|---------------------|
| recall ↑ | ловим больше аномалий (меньше FN) |
| precision ↑ | меньше ложных тревог (меньше FP) |
| fn | пропущенные аномалии (критично при β>1) |
| fp | нормальные, помеченные как аномалия |

Числа valid/test считаются **только по соответствующей выборке** (595 строк каждая при 70/15/15 от 3233). Таблица metrics на 2000+ строк обычно означает, что в узел попал нефильтрованный поток.

## Визуальная схема

- Переименование и нумерация **не меняют** расчёт.
- Нумерацию делать по `Guid`, отдельно на каждый `Unit`.
- Не удалять узлы «Замена» / «Фильтр» с холста — только сдвигать/переименовывать, если они в рабочей цепочке.
